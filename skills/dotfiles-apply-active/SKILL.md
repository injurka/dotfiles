# Применение изменений dotfiles

В этом репозитории изменение действующего конфига включает его применение
к текущей системе. Пользователь разрешил этот цикл: редактирование, проверка,
резервная копия, объединение, применение и доступная runtime-проверка.
Не заканчивай работу только изменениями в Git и не запрашивай повторное
подтверждение обычного применения. Явное указание пользователя «только в репе»,
«не применять» или запрос лишь анализа имеет приоритет.

## Область применения

Определи корень репозитория через Git; для установленного глобально навыка
стандартный checkout — `/home/injurka/my/dotfiles`. Источник end-4 —
`end4/home/`, назначение определяется по фактической запущенной сессии,
XDG-путям, launcher и симлинкам, а не по предположению о `$HOME`.

Перед изменениями сохрани исходное содержимое затрагиваемых файлов и проверь
Git status. По завершении переноси только изменения текущей задачи, включая
необходимые новые файлы и удаления; чужое dirty-дерево не является списком
разрешённых обновлений. Запрос пользователя «применить» включает рабочую
копию этой задачи, даже если она ещё не закоммичена.

Для end-4 прочитай `end4/skills/end4-update-active-config/SKILL.md` и используй
его процедуру baseline, merge, backup, validation и state. При правке одного
компонента выполняй её в пределах этого компонента; полная синхронизация
репозитория нужна только при соответствующем запросе. Ревизия и хеши такого
применения относятся к указанной области, а не ко всей установленной системе.

Если файл ещё не учтён в state, сравни активную версию с сохранённой версией
до правок и историей Git. Точное совпадение даёт базу этому файлу, но не всему
конфигу. Если обе стороны менялись, объедини их по смыслу. Не затирай
неразобранные локальные изменения. Проверяй, что файл не изменился между
подготовкой и записью. Не используй `install.sh --configs-only` для обновления.

Для остальных dotfiles используй тот же принцип: определить реального
потребителя файла, сохранить локальные настройки, подготовить и проверить
результат, создать резервную копию, применить только область задачи.

## Загрузка и завершение

После записи проверь, что приложение подхватило изменения. Если Quickshell
сам перезагрузил QML, достаточно подтвердить успешную загрузку в логах;
дополнительный перезапуск не нужен. При необходимости используй поддерживаемую
мягкую перезагрузку конкретного компонента. Не завершай Hyprland, пользовательскую
сессию или несвязанные службы. Ошибка загрузки требует отката затронутого
изменения и проверки восстановления.

Сохраняй существующий state других компонентов. Для области задачи записывай
источник, dirty-признак, baseline и хеши результата; не представляй локальное
обновление как полное обновление всех файлов до HEAD. Не меняй пользовательские
данные, мониторные настройки и секреты ради применения UI.

Ограничения sandbox решай штатным запросом расширенных прав для конкретных
разрешённых записей. Если сессия отсутствует, обнови установленный конфиг и
явно укажи невозможность живой проверки. При конфликте или недоступной записи
заверши независимую работу и точно обозначь неприменённую часть.

В ответе сообщи, что применено, результат статической и runtime-проверки,
путь резервной копии и способ отката. Различай успешную загрузку QML и
визуальную проверку изменённой панели.
